# T 모지 특성화고 모드 구현 범위

## 출시 전략

첫 단계에서는 별도 앱을 복제하지 않고 기존 T 모지 안에 `일반고`와 `특성화고` 모드를 둔다. 공통 로그인, 시즌, 지원 슬롯, 예측 결과 UI는 공유한다. 특성화고 모드는 전형 검색과 지원 자격 안내만 별도로 구성한다.

별도 스토어 앱이 필요해질 경우에도 저장소를 복사하지 않는다. 같은 코드베이스에서 동적 Expo 설정과 `APP_VARIANT`로 이름, 아이콘, 번들 식별자, EAS 제출 대상을 전환한다.

## 선행 백엔드 계약

백엔드는 Hub 저장소의 `Hub-Backend/src/modules/mock-application/`에서 변경한다. 이 저장소에는 서버 코드나 Prisma 스키마를 추가하지 않는다.

문자열에 `특성화고`가 포함됐는지만 검사하면 동일계·재직자·대학별 명칭 차이를 놓치므로, Hub가 모집단위별 대상 유형을 권위 있게 분류해야 한다.

권장 계약:

- 공개·인증 검색 API에 `audience=GENERAL|VOCATIONAL` 쿼리 추가
- 응답에 `audienceType`, `eligibilityLabel`, `sameDepartmentRequired`, `employmentRequired` 추가
- 수시와 정시 모두 같은 분류 규칙 사용
- 기존 쿼리에서 `audience`를 생략하면 현재 결과를 유지해 하위 호환 보장
- Hub 마이그레이션은 `prisma migrate deploy`만 사용

현재 프로덕션 확인 결과 수시는 `특성화고교졸업자전형`, `특성화고 등을 졸업한 재직자전형` 등이 검색되지만 정시는 명칭 구조가 달라 단순 키워드 검색으로 완전한 목록을 만들 수 없다.

## 앱 화면

1. 첫 실행 또는 홈에서 `일반고` / `특성화고` 모드 선택
2. 특성화고 모드에서 졸업(예정) 학과·계열과 재직 여부 입력
3. 지원 가능한 전형만 검색
4. 동일계·재직 요건을 모집단위 카드에 명확히 표시
5. 기존 모의지원 저장, 순위, 취소, 회원 탈퇴 흐름 재사용

## 별도 앱으로 분리할 때

- 현재 앱: `kr.tskool.mockapply`
- 특성화고 앱 후보: `kr.tskool.mockapply.vocational`
- 표시명: `T 모지 (특성화고)`
- 별도 App Store Connect/Google Play 앱과 스토어 자산 필요
- 별도 앱은 이름과 필터만 다른 복제본이 아니라 지원 자격 확인, 동일계 판정, 특성화고 전용 안내처럼 독자 기능을 갖춘 후 제출

Expo 설정은 `app.config.ts`에서 `APP_VARIANT=general|vocational`을 읽고 `name`, `slug`, `ios.bundleIdentifier`, `android.package`, 아이콘, EAS 제출 대상을 전환한다.

## 일주일 우선순위

1. 기존 T 모지의 비회원 진입 수정 빌드 재제출
2. Hub의 특성화고 분류와 검색 계약 구현·배포
3. 기존 앱에 특성화고 모드 연결
4. 내부 테스트 후 기존 앱 업데이트로 먼저 배포
5. 별도 앱의 실익과 스토어 중복 정책을 검토한 뒤 변형 빌드 생성
